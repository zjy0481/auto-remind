# Agent 完成任务后手机通知：调研与建议

调研日期：2026-09-27。使用环境：Windows 上的 Codex，手机为三星 S25 Ultra（Android）。本次只调研，未安装工具、配置凭据或发送通知。

## 结论

建议先做 **显式调用的 Codex Skill + 本地发送脚本 + PushPlus**。如果需要作为标准 tool 暴露，或之后接入多个 agent 客户端，优先评估官方本地 MCP，仅在它不满足范围或去重要求时再做专用封装。无需另起一个负责推理的 agent，也无需为第一版部署公网服务。

通知渠道的官方依据、额度和限制见 [渠道调研](notification-channels.md)。PushPlus 优先是基于用户已有使用经验和希望在微信接收的偏好；手机实际锁屏提醒与延迟仍需验证。

## 可复用的现成实现

PushPlus 已发布官方 TypeScript/Java MCP，TypeScript 版本包名为 `@perk-net/pushplus-mcp-server`，官方提供 Windows 配置示例。因此若要求真正的 tool，优先评估复用官方 MCP，而非重复开发发送接口。[PushPlus MCP 文档](https://www.pushplus.plus/doc/guide/mcp.html)

官方也提供通知 Skill，但文档说明发送前先展示摘要并等待确认，包含群组、好友等更广泛能力。这与本需求的“提前显式授权、任务完成后无需守在电脑前再次确认”不完全匹配。建议采用专用完成提醒 Skill，复用 API 或审核后的官方 MCP，仅暴露所需发送能力；本次并未安装或读取其技能包，未进行代码审计。[PushPlus Skill 文档](https://www.pushplus.plus/doc/guide/skill.html)

发送消息只需 `PUSHPLUS_TOKEN`；开放接口查询结果则需要用户 token、secretKey、开启开放接口及安全 IP 配置。因此最小方案先报告“已受理”，无需为宣称到达而扩大凭据权限。密钥放在本地环境配置中，不要求粘贴到聊天。[PushPlus 凭证说明](https://www.pushplus.plus/doc/guide/skill.html)

## 接入形式比较

| 形式 | 使用方式 | 适用性 |
|---|---|---|
| Skill + 脚本 | 显式点名通知 Skill；agent 完成任务后运行发送脚本 | 本次个人 Codex 使用的最小方案 |
| Skill + 本地 MCP | Skill 管理使用规则，MCP 提供 `notify_task_done` 工具 | 希望工具出现在工具列表、或多个支持 MCP 的宿主复用时采用 |
| 宿主事件 Hook + 授权状态 | 记录本次授权，在结束事件发生时检查再发送 | 对漏发要求更高时研究，需适配宿主事件和状态 |

Codex 支持本地 stdio MCP 和远程 Streamable HTTP MCP；本地服务可以由宿主启动，并通过环境变量接收配置。因此本地通知 MCP 不要求公网入口。[官方 MCP 文档](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)

Skill 是工作流指令及可选脚本的载体。Codex 支持显式调用，并允许在 `agents/openai.yaml` 设置 `policy.allow_implicit_invocation: false` 关闭隐式激活。[官方 Skill 文档](https://learn.chatgpt.com/docs/build-skills)

上述关闭开关控制的是 Skill 激活，不是底层脚本或 MCP 的权限隔离。普通 MCP 调用参数由模型生成；给工具加 `authorized=true` 参数，并不能独立证明用户确实授权。

## 第一版建议的行为约定

以下为设计建议，尚未实现：

1. 用户明确使用通知 Skill/tool，例如“使用完成提醒，修复这个问题并验证，完成后通知我”。仅当前指定任务生效，不自动扩展到之后的每次对话。
2. 等待任务本身及必要验证结束，再发送一条完成通知；提出方案、等待用户输入、子任务结束都不视为整体完成。
3. 通知只包含任务名、结果摘要、验证情况。默认不上传完整聊天记录、源码、凭据。收件人固定为预先配置的自己。
4. 每次任务使用稳定标识做去重。发送超时可能是响应丢失，不能直接认定未发送并无限重试。
5. 明确区分“服务已受理”“渠道发送成功”和“手机已显示/用户已读”。工具不得把第一种状态描述成第三种。
6. 通知失败不改变原任务的完成状态；在最终答复中单独报告通知失败。
7. 失败、被中断、需要用户操作等状态暂不自动推送；如果以后希望“结束就提醒”，应单独扩展约定，不能一律标记为完成。

单靠 Skill 指令仍可能漏调用，程序退出也可能阻止发送。它适合低频个人提醒，不能承诺绝不漏发或绝不误触发。若需要严格执行“未授权绝不发”，应由可信宿主输入/明确的界面操作生成任务授权，发送端校验；仅由模型生成授权标志不够。

## 何时考虑 Hook

Codex 官方提供 `Stop` 等 Hook 事件，`Stop` 载荷包含 `turn_id` 等字段。但一轮停止不等于用户要求的整个任务成功完成，因此不能把所有 `Stop` 都映射为“任务完成”。应增加任务范围、显式授权、完成判定及去重逻辑，并在当前安装版本验证事件行为。[官方 Hook 文档](https://learn.chatgpt.com/docs/hooks)

官方配置还提供 `notify` 外部通知命令；这只是通知接入点，本身不表达本次用户是否授权或任务是否成功。[官方配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)

第一版建议先采用 Skill 主动调用发送逻辑，真实使用中确认是否存在漏发，再决定是否值得引入 Hook 状态管理。

## 实现前最有价值的验证

- 用 PushPlus 当前账号确认微信渠道、实际免费额度和手机接收设置。
- 一条用户明确授权的测试通知：电脑提交、渠道状态、三星锁屏横幅/声音分别验证。
- 覆盖未点名不发送、任务成功只发一次、失败不误报成功、网络超时不重复轰炸。
- 手机关闭/开启微信通知、锁屏、省电模式下分别观察实际表现；文档支持不能替代到机测试。

若只需“工作完成，请回电脑查看”，第一版消息可简化为任务名和一句状态，进一步减少第三方接收的数据。
